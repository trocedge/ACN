## 1. 为什么需要这份字典

截止日是本项目最关键的数据。实测发现同一含义存在多种写法（`AoE` 与 `UTC-12` 并存、`UTC` 与 `UTC+0` 并存），且部分取值无法用固定偏移表示。若不统一口径，展示层容易把 `AoE` 误当成北京时间，**导致 1540 条截止日整体偏移一天**。

## 3. 换算规则

北京时间 = 本地时间 + (8 − 原时区 UTC 偏移)

| 原时区 | 偏移 | 换算到北京时间 |
|---|:---:|---|
| `AoE` / `UTC-12` | -12 | **+20 小时** |
| `UTC-8` | -8 | +16 小时 |
| `UTC+0` / `UTC` | 0 | +8 小时 |
| `UTC+8` | +8 | +0 小时（已是北京时间） |

示例：`'2021-07-02 17:00:00'` + `AoE` → 北京时间 `'2021-07-03T13:00:00'`。**跨日必须保留**，不能只换小时不换日期。

## 4. 处理约定

| 场景 | 约定 | 落地位置 |
|---|---|---|
| 可确定偏移 | 保留 `timezone` 原值，写入 `timezone_utc_offset`，产出 `deadline_beijing` | 转换脚本 `to_beijing()` |
| `PT` 等夏令时时区 | 保留原值，偏移与换算值均为 `null`，由展示层按日期判定 | 转换脚本 `utc_offset()` 返回 `None` |
| `TBD` | 不换算、不补写 | 转换脚本 `norm_deadline()` |
| 未知写法 | 列入校验 WARN，不猜测偏移 | `scripts/validate_data.py` 白名单 |
| 参考站示例中的 `24:00:00` | **不采用**，非合法 ISO 8601 时刻；仓库实测出现 0 次，约定用 `23:59:59` | 规范文档 |

---

## 5. 归一化建议（后续，不破坏原值）

现有数据存在 `AoE` 与 `UTC-12`、`UTC` 与 `UTC+0` 语义重叠。建议分两步，均不改动原值：

1. 建立别名表（`AoE` → `UTC-12`、`UTC` → `UTC+0`）作为**展示与换算依据**；
2. 若项目组决定统一源数据写法，另开一次独立变更，逐条核对后由 PR 提交，不在本次转换中隐式改写。
