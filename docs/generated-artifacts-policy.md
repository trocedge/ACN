# 生成物入库策略说明（待项目组确认）

> 日期：2026-11-10
> 背景：仓库 `scripts/DATA_LOADING.md` 说明生成文件由 CI 组装且被 Git 忽略；
> 而本次数据格式改造将 `data/conferences.yml` 随仓库提交。两种口径需要统一。

---

## 1. 冲突点

| 来源 | 说法 |
|---|---|
| `scripts/DATA_LOADING.md` | 生成的 JSON 分片「remain ignored by Git，并在 CI 构建与部署构建中组装」 |
| 本次改造 | `data/` 未被 `.gitignore` 忽略，`data/conferences.yml`（1200.9 KB）随分支提交 |

两者并不矛盾（前者指 `public/conference/` 下的构建产物，后者是新增的数据源视图），但**若不写明边界，后续会出现「到底哪个是准的」的争议**。

---

## 2. 两个方案对比

| 维度 | 方案 A：随仓库提交产物 | 方案 B：由 CI 生成、加入 `.gitignore` |
|---|---|---|
| 前端对接 | 立即可读，不依赖构建 | 需先跑生成步骤 |
| 仓库体积 | 每次数据变更产生大 diff（当前 1.2 MB，v1.0→v1.1 增加 424 KB） | 仓库只存脚本，无大文件 |
| 数据新鲜度 | 依赖人工重跑，可能过期 | 每次 CI 自动刷新，始终最新 |
| `status` 快照 | 固化在提交时刻，会过期 | 每次构建重算，始终准确 |
| 评审可读性 | PR 里能直接看到产出内容 | PR 只有脚本，产出需看 CI 日志 |
| 失败风险 | 低（文件已在） | 生成步骤失败会导致前端无数据 |
| 适用阶段 | 界面改造对接期 | 长期稳定运行期 |

---

## 3. 当前处理（本次交付）

采用**方案 A**，理由：

1. 界面改造进行中，展示层需要一份可直接读取的数据文件用于联调；
2. 本次全部改动为新增文件，失败可直接删除回退；
3. 项目组的 CI 与 Pages 部署分工尚未落地，暂不具备自动生成条件。

同时在数据中加入 `status_as_of` 明确标注状态快照的生成时刻，避免把固化值误当成实时值。

---

## 4. 建议的演进路径

1. **对接期（当前）**：方案 A，随仓库提交。
2. **CI 落地后**：切换方案 B，把 `data/conferences.yml` 加入 `.gitignore`，
   由 CI 执行 `python scripts/build_compact_data.py` 生成后再构建部署；
   此时 `status` 每次构建重算，`status_as_of` 才有长期意义。
3. 切换时需同步更新：`docs/data-format-specification.md`、`docs/data-changelog.md`、
   `docs/ci-templates/data-check.yml` 与前端读取路径。

---

## 5. 需项目组拍板的一项

> 「生成物随仓库提交」还是「由 CI 生成并忽略」？

在确认前，本分支保持方案 A，并在 PR 描述中明确标注该待决项。**不擅自修改 `.gitignore`，也不擅自改动他人负责的 workflow。**
